# MUST PV18-3024 VPM II → MQTT → Home Assistant (ESP32-S3, RS485)

Мост между инвертором MUST PV18-3024 VPM II (совместим с протоколом
PH1800/PV1800/EP1800 серии) и Home Assistant: ESP32-S3 опрашивает
инвертор по Modbus RTU через RS485, публикует в MQTT с автоматическим
Home Assistant Discovery, отдаёт веб-интерфейс с настройками, живыми
логами и локальной историей показаний.

## Подключение к инвертору

Только **RS485** — на самом инверторе это порт **"COM"** (RJ45,
подтверждено фото панели), распиновка:

| Пин RJ45 | Назначение |
|---|---|
| 1 | RS485 B |
| 2 | RS485 A |
| 3 | GND |
| 4-8 | не используются |

Между инвертором и ESP32 нужен недорогой модуль **RS485-TTL** (лучше с
автонаправлением, тогда `uart_de_pin: -1` в конфиге, без ручного DE/RE):

- RJ45 пин 2 (A) -> модуль **A+**
- RJ45 пин 1 (B) -> модуль **B-**
- RJ45 пин 3 (GND) -> модуль **GND**
- модуль **RXD** -> ESP32 **GPIO17** (TX)
- модуль **TXD** -> ESP32 **GPIO16** (RX)
- модуль **VCC** -> 3.3V или 5V ESP32 (смотрите на конкретный модуль)
- модуль **GND** -> GND ESP32

Протокол подтверждён реальным дампом с шины: **Modbus RTU**, slave ID
`4`, baud `19200`, функция `03 (Read Holding Registers)`. Все параметры
по умолчанию в конфиге уже выставлены под это.

## Первая прошивка

```
pio run -t upload
pio device monitor
```

При первом запуске (пустой WiFi в конфиге) ESP32 поднимет точку
доступа `MUST-PV18-Setup` / пароль `12345678`. Подключитесь к ней,
откройте `http://192.168.4.1/`, заполните WiFi/MQTT/Modbus, сохраните
— устройство перезагрузится и подключится к вашей сети.

## Последующие обновления — через OTA

`http://<ip-адрес-esp32>/update` — веб-страница ElegantOTA, заливаете
новый `.pio/build/esp32-s3-devkitc-1/firmware.bin`.

## Карта регистров

63 регистра по умолчанию (`config.cpp`) взяты из открытой Home Assistant
интеграции [mukaschultze/ha-must-inverter](https://github.com/mukaschultze/ha-must-inverter)
(MIT), протестированной именно на PV18-3024 VPM. Это не догадки —
реальные адреса, масштабы, единицы измерения.

`is_signed` для части полей (реактивная мощность, ток/мощность батареи,
температуры) проставлен вручную по физическому смыслу — в оригинальном
`const.py` этого нет явно, там своя логика на стороне pymodbus. Если
увидите переполненные/дикие значения на каком-то регистре — вероятно,
ему тоже нужен `is_signed: true` (правится в вебе без перепрошивки).

### Формат JSON регистров (редактируется прямо в вебе)

```json
[
  {"name": "ac_voltage", "address": 25202, "count": 1, "is_signed": false, "scale": 1.0, "unit": "V"},
  {"name": "battery_ch1", "address": 25206, "count": 1, "is_signed": false, "scale": 0.01, "unit": "V"}
]
```

`count: 2` — для 32-битных значений (два регистра, старшее слово первым).

### Дальнейшая реверс-инженерия регистров

Расширяйте диапазон опроса через Modbus Poll на компьютере, сверяйте с
показаниями на ЖК-панели инвертора при разных состояниях (нагрузка
вкл/выкл, есть заряд от PV или нет) — и добавляйте найденные регистры в
JSON через веб-интерфейс.

## Home Assistant MQTT Discovery

Работает из коробки: при каждом подключении к брокеру ESP32 сам
публикует конфигурацию сенсоров в `homeassistant/sensor/.../config`
(с `retain`). В HA нужна только обычная интеграция MQTT с включённым
Discovery (это дефолт).

`state_class` проставляется автоматически: `total_increasing` для
накопительных `kWh`-счётчиков (нужно для Energy Dashboard), `measurement`
для мгновенных величин (V/A/W/VA/var/Hz/%/°C).

## Дача → город через белый IP (TLS)

Если инвертор на даче, а MQTT-брокер (или Home Assistant) — в городе за
белым IP: включите `mqtt.tls` в веб-конфиге.

Реализация через `WiFiClientSecure::setInsecure()` — канал шифруется
(перехват трафика по пути через интернет не даст ничего полезного), но
сертификат брокера не проверяется (нет защиты от активной MITM-подмены,
только от пассивного прослушивания). Обязательно смените порт брокера
на TLS-listener (обычно `8883`, не `1883`) — иначе включать `tls: true`
бессмысленно, соединяться будет некуда.

Если нужна полная проверка сертификата — в `mqtt_handler.cpp` замените
`s_secureClient.setInsecure()` на `s_secureClient.setCACert(ca_pem)` со
своим CA-сертификатом.

## Локальная история (таблица + график в вебе)

Показания копятся локально в PSRAM (`history.cpp`), независимо от
MQTT/WiFi — можно смотреть даже если Home Assistant вообще не настроен.
На главной странице — выбор регистра, график (обычный canvas, без
внешних библиотек и CDN — работает даже в AP-режиме настройки без
интернета) и таблица.

Настраивается в веб-интерфейсе: включить/выключить, глубина в часах (по
умолчанию 24ч, максимум жёстко ограничен 72ч в коде — защита от
случайной гигантской аллокации PSRAM). Реальная ёмкость в записях
считается автоматически под текущие `poll_interval_ms` и число
регистров, точная цифра — в логах при старте.

Таймстампы — через NTP (`configTime()` при подключении к WiFi). Пока
NTP не засинхронизировался, время будет показывать 1970 год — веб-страница
это распознаёт и явно предупреждает.

## RGB-индикатор состояния

Одиночный WS2812/NeoPixel на плате используется как статус-индикатор
(`src/status_led.cpp`):

| Цвет | Мигает? | Значит |
|---|---|---|
| Жёлтый | быстро | Точка доступа для первичной настройки WiFi |
| Синий | мигает | Подключение к WiFi в процессе |
| Оранжевый | мигает | WiFi есть, MQTT-брокер недоступен |
| Красный | мигает быстро | Инвертор не отвечает по RS485 |
| Зелёный | ровно, редкий "вдох" | Всё работает штатно |
| Фиолетовый | пульсирует | Идёт OTA-обновление, не отключайте питание |

Пин и яркость настраиваются в веб-интерфейсе. GPIO48 подтверждён
официальной документацией Espressif на ESP32-S3-DevKitC-1 ("RGB LED,
Addressable RGB LED, driven by GPIO48") — https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s3/esp32-s3-devkitc-1/user_guide_v1.0.html

## Отдельная задача Modbus (ядро 0)

Опрос Modbus выполняется в отдельной FreeRTOS-задаче, физически
закреплённой на **ядре 0** (`xTaskCreatePinnedToCore`), тогда как
веб-сервер/OTA/MQTT/индикатор — в обычном Arduino `loop()` на **ядре 1**.
Это настоящий параллелизм на разных ядрах, а не "по очереди в одном
потоке" — веб-интерфейс физически не может подвиснуть из-за Modbus,
даже теоретически.

Результаты передаются в основной `loop()` через тонкую FreeRTOS-очередь
(только индекс регистра + число, без строк) — `mqttPublishValue()`,
`historyPush()` и логирование живых данных по-прежнему вызываются
только из основного потока, поэтому `history.cpp` и MQTT-клиент не
пришлось защищать мьютексами: их трогает только один "поток управления".

**Что реально пришлось защитить:**
- `log_buffer.cpp` — теперь пишут одновременно и фоновая Modbus-задача,
  и основной поток, и системные задачи ESP-IDF (через перехват
  `ESP_LOG`) — добавлен рекурсивный мьютекс.
- `g_config` — фоновая задача читает `g_config.registers` постоянно;
  чтобы веб-сервер мог безопасно целиком заменить конфиг при сохранении
  настроек, задача Modbus **приостанавливается** (`modbusTaskPause()`)
  на время замены и возобновляется, если сохранение не удалось
  (`web_server.cpp`). Это проще и дешевле, чем городить мьютекс вокруг
  `g_config` во всех местах проекта, где он читается.

## Групповое чтение регистров

Соседние по адресу регистры читаются **одним** Modbus-запросом вместо
запроса на каждый (function 03 умеет читать целый диапазон разом). Для
набора из 63 регистров это обычно сжимается всего до **5 запросов** за
полный проход вместо 63 -- на порядок быстрее и меньше нагрузки на
RS485-шину.

Потолок группы -- 60 слов (не 125, как в спецификации Modbus): у
библиотеки `ModbusMaster` внутренний буфер ответа физически ограничен
64 словами (`ku8MaxBufferSize`), больше не влезет. Соседние регистры с
разрывом между ними не больше 10 слов объединяются в одну группу
автоматически при каждой смене списка регистров (пересчитывается
заново при сохранении конфига).

Ошибка чтения относится ко всей группе целиком -- логируется как есть,
без повторных попыток/исключения из опроса (карантин по отдельным
регистрам убран из проекта как избыточный: весь список регистров
подтверждённо рабочий на этой модели инвертора).

## Запись параметров в инвертор

Основной способ — прямо из Home Assistant через **Number/Switch/Select**
сущности (см. соответствующие разделы выше) с мгновенным подтверждением.

Отдельная форма записи в веб-интерфейсе устройства убрана как
избыточная (HA удобнее для этого же самого). Серверный API остался —
`POST /api/modbus/write` с телом `{"name": "...", "value": ...}` —
работает **независимо от MQTT**, полезно как fallback для диагностики
(например, curl-ом), если брокер/HA временно недоступны.

## Регистры-перечисления (enum) -- расшифровка кодов в текст

Некоторые регистры (например `WorkState` -- режим работы инвертора:
Line/Battery/Bypass) хранят не физическую величину, а код состояния из
фиксированного набора. Для них можно указать `enum_map` — объект
код→текст:

```json
{
  "name": "WorkState",
  "name_ru": "Режим работы",
  "address": 25201,
  "count": 1,
  "is_signed": false,
  "scale": 1,
  "unit": "",
  "writable": false,
  "enum_map": {
    "0": "Включение",
    "1": "Самотест",
    "2": "Батарея",
    "3": "Сеть",
    "4": "Bypass",
    "5": "Стоп",
    "6": "Заряд от сети"
  }
}
```

Если `enum_map` указан — в MQTT публикуется текст ("Bypass") вместо
числа, а в Home Assistant discovery — `device_class: enum` со списком
допустимых состояний (`options`), а не обычный числовой сенсор с
графиком. Локальная история (`history.cpp`) при этом продолжает
хранить и показывать число — строить график по тексту бессмысленно,
а для отслеживания "как часто менялся режим" числовой код вполне годится.

Код, которого нет в `enum_map` (незнакомое/новое состояние), просто
отображается как число — ничего не теряется молча.

## Битовые маски (несколько флагов одновременно)

Для регистров-масок ошибок/предупреждений (например `ChargerErrorMessage`)
используется `bit_map` — как `enum_map`, но ключ это номер **бита**, а не
всего значения целиком, потому что активными могут быть сразу несколько
флагов:

```json
{
  "name": "ChargerErrorMessage",
  "name_ru": "Код ошибки контроллера заряда",
  "address": 15213, "count": 1, "is_signed": false, "scale": 1, "unit": "", "writable": false,
  "bit_map": {
    "0": "Hardware protection",
    "4": "PV voltage is too high",
    "5": "PV voltage is too low",
    "6": "Battery voltage is too high",
    "7": "Battery voltage is too Low"
  }
}
```

В MQTT публикуется `"OK"`, если значение `0`, иначе список активных
флагов через запятую (например `"PV voltage is too low"`, а если бы
было активно сразу два — `"PV voltage is too low, Over temperature"`).
Установленный бит, которого нет в карте, отображается как `"bitN"` —
чтобы не потерять сигнал молча, даже если карта неполная.

**Ограничение:** битовые маски шире 32 бит (2 слова) не поддерживаются
— в нашей карте это касается `InverterErrorMessage` (реально 4 слова,
64 бита), он читается только как обычное число (0 = ок, что угодно ещё
= проблема) без побитовой расшифровки, пока не появится подтверждённая
раскладка по словам.

## Слайдеры в Home Assistant (запись прямо из интерфейса HA)

Регистры с `writable: true` теперь публикуются в MQTT Discovery не как
обычный сенсор, а как HA **`number`**-сущность (слайдер) — с
`command_topic` (`<prefix>/<name>/set`), на который прошивка **впервые
в проекте подписывается** (раньше только публиковала, никогда не
принимала входящие MQTT-сообщения).

Как это работает:
1. Двигаете слайдер в HA → HA публикует новое значение в `.../set`.
2. Прошивка получает это через `PubSubClient::setCallback()`, находит
   регистр по имени топика, переводит в сырое значение по `scale` и
   реально пишет в инвертор через `modbusWriteRegisterSync()` (тот же
   код, что и у ручной записи в вебе).
3. Если инвертор подтвердил запись — новое значение сразу публикуется
   обратно в `state_topic`, HA видит подтверждённое значение без
   ожидания следующего цикла опроса.
4. Если запись не удалась — ничего не публикуется, и при следующем
   обычном опросе слайдер в HA откатится на реальное текущее значение
   (честный результат вместо оптимистичного вранья).

Диапазоны (`min`/`max`/`step`) для 14 регистров по умолчанию взяты из
`RANGES` в исходной карте `ha-must-inverter`, **зафиксированы под 24В
систему** (у оригинала часть диапазонов зависит от `BattVolGrade`,
которое мы не считываем и не пересчитываем динамически — для 24В банка
коэффициент равен 1, так что значения статические и верные именно для
24В; если у вас 48В — поправьте `min`/`max` вручную в JSON).

## Переключатели (Switch) в Home Assistant

Регистры с `writable: true` и `is_switch: true` публикуются как HA
**`switch`**-сущность (тумблер) вместо слайдера — используется тот же
`command_topic`/подписка/`modbusWriteRegisterSync()`, что и у number,
разница только в представлении: состояние и команды — простые `"1"`/`"0"`
(без текстовых `ON`/`OFF`, чтобы не городить отдельную схему сравнения).

```json
{
  "name": "ChargerWorkEnable", "name_ru": "Работа контроллера заряда",
  "address": 10101, "count": 1, "is_signed": false, "scale": 1, "unit": "",
  "writable": true, "min": 0, "max": 1, "step": 1, "is_switch": true
}
```

По умолчанию добавлены 5 переключателей, которые в исходной карте
`ha-must-inverter` помечены как `enabled: True` (то есть автор
интеграции считал их безопасными по умолчанию): `ChargerWorkEnable`,
`BatteryEqualizationEnable`, `InverterOffgridWorkEnable`,
`InverterSearchModeEnable`, `SolarPowerBalance`. Ещё 4 похожих регистра
(`InverterOngridWorkEnable`, `InverterChargerFromGridEnable`,
`InverterDischargerEnable`, `InverterDischargerToGridEnable`) в
оригинале были выключены по умолчанию (`enabled: False`) — не добавлены
намеренно, но можно добавить вручную по тому же шаблону, если понадобятся.

## Выпадающие списки (Select) в Home Assistant

Регистр с `enum_map` **и** `writable: true` вместе публикуется как HA
**`select`**-сущность (выпадающий список) вместо обычного enum-сенсора.
Отличие от чтения: HA присылает в `command_topic` **текст** выбранного
варианта (не код), поэтому `onMqttMessage()` делает обратный поиск
текст→код по той же `enum_map`, что используется для расшифровки при
чтении — не нужна отдельная карта в обе стороны.

```json
{
  "name": "BatteryType", "name_ru": "Тип батареи",
  "address": 10110, "count": 1, "is_signed": false, "scale": 1, "unit": "",
  "writable": true,
  "enum_map": {"0": "Не задано", "2": "Литий", "6": "Заливная"}
}
```

Три HA-сущности из writable-регистров теперь выбираются автоматически
по сочетанию полей — ничего дополнительно указывать не нужно:
- `writable + is_switch` → **switch**
- `writable + enum_map` → **select**
- `writable` (без того и другого) → **number**

## Доступ к веб-интерфейсу (HTTP Basic Auth)

Весь веб-интерфейс и API (кроме `/update`, у него свой отдельный
`ota_password`) можно защитить логином/паролем — поле в веб-конфиге,
пусто по умолчанию (защита выключена, чтобы не оказаться запертым при
первой настройке через AP-режим).

Как только зададите пароль и сохраните — при следующей загрузке
страницы браузер запросит логин/пароль стандартным диалогом (обычная
HTTP Basic Auth, без отдельной формы входа). Последующие AJAX-запросы
(конфиг, логи, история) браузер аутентифицирует автоматически — это
штатное поведение Basic Auth, ничего дополнительно в JS для этого не
делалось.

**Не забудьте пароль** — сброс возможен только полной переустановкой
конфига (стирание LittleFS/переприкладка через отдельную прошивку с
пустым паролем), обычного "забыл пароль" тут нет.

## Датчик температуры/влажности SHT41 (I2C, локальный)

Измеряет условия в месте установки ESP32/инвертора — не связан с
Modbus вообще. Подключение: SDA/SCL (по умолчанию GPIO8/GPIO9,
настраивается в веб-конфиге) + питание 3.3В.

Интегрирован в тот же пайплайн, что и обычные регистры: два
"виртуальных" значения `AmbientTemperature`/`AmbientHumidity` в списке
регистров с флагом `is_local: true` — задача опроса Modbus их
пропускает при построении групп чтения (см. "Групповое чтение" выше),
а сам модуль `temp_humidity.cpp` публикует их напрямую через
`mqttPublishValue()`/`historyPush()` раз в 30 секунд. Discovery,
история, график в вебе — всё работает автоматически, без отдельного
кода под это.

По умолчанию выключен (`sht41_enabled: false`) — включите в веб-конфиге
после физического подключения датчика.

**Не проверено сборкой** — API библиотеки `Adafruit_SHT4x`
(`getEvent`/`sensors_event_t`) приведён по типовому паттерну Adafruit
Sensor библиотек, не по факту скомпилированного проекта. Если сигнатура
разойдётся с установленной версией — компилятор укажет точную строку.

## Плата

ESP32-S3-DevKitC-1 N16R8 (16MB flash QIO + 8MB PSRAM OPI) — точные
настройки памяти уже в `platformio.ini`. При смене платы на другой
вариант памяти поправьте блок "Точная память вашей платы" там же.

## Почему не USB Host

Изначально рассматривался вариант подключения через USB-B инвертора
напрямую (ESP32-S3 как USB-хост). От него отказались: на обычном
ESP32-S3-DevKitC-1 нативный OTG-порт физически не подаёт VBUS (+5В) на
подключаемое устройство — это аппаратное ограничение платы (нужна
специальная ESP32-S3-USB-OTG с переключением питания, либо доработка
проводки), а не то, что можно починить прошивкой. RS485 не имеет этого
ограничения и не требует никаких доп. плат, кроме простого RS485-TTL
конвертера.
